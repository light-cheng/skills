# Decide

A **Bounded judgment** is a closed-set question that a workflow can act on: picking one of several options (`choice`), answering a binary gate (`yes_no`), rating an ordered rubric (`score`), or evaluating one question set across multiple states (`decide_batch`). `decide` evaluates the question through `light-decision-mcp` within the repository's privacy boundary, gates application on calibration policy, falls back transparently to agent self-judgment when needed, and logs an audit row under `.scratch/`.

## Scope boundary

Evaluate only closed-set judgments the caller could make itself (such as `redirect/is-direction-change`, `agent-config/task-complexity`, `agent-config/reasoning-need`, or `manuscript-ops/route`). Leave open-ended design choices, human approval of a spec, ticket graph, or Change proposal (`redirect`), `acceptance` verdicts (`PASS`, `FAIL`, `BLOCKED`), and host permissions to the human or execution evidence.

When only one option is legal, skip external backends, log the single option as a self-judgment (`fallback_reason: none`), and return it immediately.

## Steps

1. **Frame the judgment.** Collect the legal options or ordered levels (lowest first), active `<feature>` slug if any, and stable `question_id` (`<caller>/<slug>`, or `decide/<kebab-slug>` when standalone). Select the matching shape (`yes_no`, `choose`, `score`, multi-question `decide`, or multi-state `decide_batch`). Build a minimal `state` holding only the excerpt and facts the question requires; exclude credentials, personal data, and unnecessary source code or diffs. Attach `images` (up to 4) only when visual inspection is part of the judgment. *Done when `question_id`, plain-language question, kind, options or ordered levels, and minimal `state` (plus optional `images`) are set.*
2. **Enforce the `Decision data` boundary.** Read `Decision data` in `docs/agents/light-project.md` (ignoring fenced code blocks; if multiple settings appear, the strictest wins across `off < on-device < private-network < third-party`). Missing file or missing setting defaults to `on-device`. When `Decision data` is `off` or unrecognized, make zero MCP calls, answer by agent self-judgment with `fallback_reason: off` (reporting any unrecognized value to the caller), and jump to Step 6. Active-run prompts or caller arguments may narrow this ceiling for one call, never widen it. *Done when effective `max_data_destination` (`on-device`, `private-network`, or `third-party`) is locked or `off` has routed to self-judgment.*
3. **Probe and select a route.** Follow [`references/routing.md`](references/routing.md) to check `light-decision-mcp` readiness in this session via read-only `status`, constrain routing to `max_data_destination` (adding `mode: "local_only"` when the ceiling is `on-device`), and enforce the multimodal `images` safety gate whenever `images` are present. When `light-decision-mcp` is absent or no allowed backend is ready, finish the current judgment by self-judgment (`fallback_reason: unavailable` or `images-unsupported`); if upcoming work would clearly benefit from a typed decision backend and setup was not previously declined, offer setup once after returning via [`references/setup.md`](references/setup.md). *Done when one verified `light-decision-mcp` route within `max_data_destination` is chosen, or self-judgment fallback is selected.*
4. **Call `light-decision-mcp`.** Invoke `yes_no`, `choose`, `score`, `decide`, or `decide_batch` per [`references/routing.md`](references/routing.md), always passing `max_data_destination` and keeping `allow_image_drop_on_fallback: false` unless text-only fallback was explicitly authorized. Convert any timeout, circuit-open fault, `data_boundary_exceeded`, `images_unsupported`, or malformed payload into an immediate single-pass fallback to self-judgment rather than retrying. *Done when a normalized MCP response envelope is returned or a single-pass fault has switched to self-judgment.*
5. **Normalize and gate on calibration policy.** Using [`references/formats.md`](references/formats.md), match the actual answering backend and model (`response.backend` and `response.model`, accounting for `fallback_used: true`) against `~/.config/light/decision-policy.json`. Set `applied: true` and `final = answer` (`fallback_reason: none`) only when that backend has a valid calibration entry for `question_id` and `confidence >= min_confidence`. Otherwise retain the typed `answer`, `score`, `probabilities`, and `confidence` on record (`applied: false`, `fallback_reason: uncalibrated` or `low-confidence`) and set `final` from your own self-judgment. *Done when all normalized fields (`level`, `label`, `expected_level`, `score`, `probabilities`, `confidence`, `provider_confidence`, `data_destination`, `fallback_used`, `applied`, `fallback_reason`, `final`) are populated.*
6. **Log to `.scratch/`.** Append one row per judgment to `.scratch/<feature>/decisions.md`, or `.scratch/decisions.md` when no `<feature>` directory is active (never write `decisions.md` in the repository root), following [`references/formats.md`](references/formats.md). In a read-only workspace, return the formatted row to the caller instead. *Done when the audit row is appended under `.scratch/` (or attached for a read-only caller).*
7. **Return to the caller.** Return the normalized result (`final` as the decision to act on, alongside full distribution and provenance fields for callers such as `agent-config`) and stop. *Done when the caller receives the normalized result.*

## Caller and subagent contract

- **Graceful fallback**: When `light-decision-mcp` is absent, offline, `off`, or uncalibrated, callers (`redirect`, `agent-config`, `manuscript-ops`, or ad-hoc workflows) proceed seamlessly on `final` and never report `BLOCKED` over missing decision tooling.
- **Caller records context first**: Callers write their own domain artifacts (`redirect` Change proposals, `acceptance` charters) independently; `decide` writes only the judgment row under `.scratch/`.
- **Returns without taking over**: `decide` hands back a structured result and never triggers user-invoked skills, edits specs or tickets, or overrides permissions or `acceptance` verdicts.
- **Fresh-context subagents**: If a helper subagent is ever dispatched (for example, scoring held-out batches during user-requested calibration), start it with a **fresh context window**, never a fork of the current conversation.
